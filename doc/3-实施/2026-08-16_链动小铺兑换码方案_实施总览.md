# 需求实施总览：链动小铺外跳收款 + 兑换码核销（new-api）

结论：复用现有兑换码体系，把"链动小铺外跳收款"与"兑换码核销加额度"两段解耦，通过新增兑换码档位预设、独立启用开关、核销补账单与 int32 饱和保护，让管理员能按 $5/$10/$20/$50/$100/$500 一键批量生成兑换码，用户在钱包页点外链去链动小铺付款后回来粘贴兑换码核销；影响：用户、管理员（创建兑换码、对账）、无需新增支付通道/webhook；范围：档位预设、独立开关、Redeem 加 TopUp 记录、复用 `creditTopUpQuota`、前端创建抽屉档位按钮、管理后台配置项；非范围：不动钱包页 UI、不动任何支付路由、不改 Redemption 表 schema、不改错误细分、不做一码多人兑；变化：管理员创建兑换码不再要求先确认支付合规，兑换后充值历史可见；完成标准：创建页出现档位按钮、兑换加额度并写 TopUp、关闭支付合规后仍可创建/兑换、超大额兑换被 int32 截断且审计；术语说明：兑换码=redemption code，档位=tier（面额），合规确认=支付合规条款确认；验证状态：计划编写中，实施后以新增单测 + go build + 手工路径验证为准。

## 1. 当前计划最终方案简要说明
- 推荐方案一句话结论：不改任何支付通道，用现有 `POST /api/user/topup` + `model.Redeem` 承接链动小铺发码后的核销，前端/后台只做档位预设与独立开关的增量改造。
- 主落点 / 主路径：`setting/operation_setting/redemption_setting.go`（档位+开关）→ `model/redemption.go`（核销记账加固）→ `controller/{redemption,topup,user}.go`（解耦+下发）→ 前端 `redemptions-mutate-drawer.tsx`（档位按钮）→ 后台设置项。
- 为什么先走这条路线：现有兑换码链路（事务+行锁+CAS 幂等+过期）已满足链动小铺"一码一人"模型，零新增支付 provider/webhook，改动面最小、风险最低。

## 7. 方案选择
- 方案 A（推荐）：复用现有兑换码链路 + 增量改造（档位、独立开关、账单、饱和保护）。改动面小、风险低、复用现有事务/行锁/CAS。
- 方案 B：新建独立兑换码表 + 新核销接口。改动大、重复造轮子，不必要。
- 方案 C：在支付网关项目里做链动小铺。与本方案目标（new-api 侧核销）不符，且支付网关已放弃。
- 推荐方案与原因：方案 A。理由：主链路已存在，只需补齐档位/开关/记账三块增量，符合"最小改动"与"复用现有实现"原则。
